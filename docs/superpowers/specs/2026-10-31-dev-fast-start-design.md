# `gsx dev` fast start

## Problem

`gsx dev` does three things one after another before the app is reachable:

1. **Arm the watch session**, including `ValidateConfiguredMergers`, which loads the shared world through `packages.Load`.
2. **Initial generate**, which analyzes and generates every GSX dir in the session's Module, one dir at a time.
3. **Build and start the server**, through `devServer.rebuild`: the configured `build` command, then `run`.

On eos (639 packages, 192 GSX dirs), steps 1 and 2 take 2.5s and 4.5s on an idle machine, and about 12s together under load. Step 3's `go build` waits behind them. Meanwhile eos's `task dev` has normally just run `gsx generate`, so the initial generate rewrites nothing. A warm `gsx generate` produces the same result in 0.66s from the persistent cache.

Edit cycles are already fast (~0.2s) and are not in scope.

## Goal

The time from `gsx dev` start to a healthy server is bounded by the build, not by gsx. What gets generated, written, reported and served must not change.

The user accepted one tradeoff: an edit saved during the first seconds after startup, before the background warm-up finishes, may take a few seconds instead of ~0.2s.

Non-goals:
- eos's own steps: migrations, `npm ci`, the duplicated generate and sqlc runs in `task dev`, and the build command itself.
- The LSP.
- Parallelizing `Module.Generate`, which `analysisMu` serializes.

Anti-goals:
- A startup that serves a binary built from `.x.go` files that changed after the build started.
- A startup that reports different diagnostics or different written/removed files than today.

## Design

### 1. Cached initial generate

After the watch session is armed (unchanged: observation is armed before the startup snapshot), the initial generate goes through the persistent generate cache, the same pipeline as `gsx generate` (`prepareCache` → `classifyCache`):

- **Cache hits** are restored exactly as `commitCache` restores them. The bytes are written only if they differ from disk, and the cached warnings are kept. Each hit becomes a `cycleResult` carrying the same `Written` and `Diags` today's initial generate would produce.
- **Misses and uncacheable dirs** are generated by the session's own Module (`regenDirs`), exactly as today, not by a separate `GenerateDirs`.
- **Misses are not stored to the cache from `gsx dev`.** The session Module re-reads disk after the key is computed, so storing could pair a key with newer sources. eos's `task dev` runs `gsx generate` first, and that run stores. (My call.)
- **The orphan sweep** (`sweepOrphanStartup`) runs once, before generation, exactly as today.
- **Startup results** feed the dev panel, overlay and `dirty.retainOperational` unchanged.

If the cache is disabled or the module is uncacheable, every dir is a miss, which is today's behaviour.

### 2. Merger validation runs in the background but stays fatal

`ValidateConfiguredMergers` moves out of the synchronous part of `prepareWatchSession`. It starts in the background as soon as the session is armed. It runs on the session Module, so it is serialized with any Module `Generate` by `analysisMu`.

Its outcome is still fatal and still comes before anything is served. `gsx dev` waits for the validation result before it starts `run` (`restartNoBuild`). On failure it prints the same error and exits 1, as today.

The build takes far longer than the 2.5s validation, so this wait costs nothing on eos. Hits may already have been restored by then. Those bytes equal what a validated run produced, because the merger's package sources are part of the cache key. (My call.)

### 3. Speculative build

The configured `build` command starts as soon as `armWatchSession` has returned, and never earlier. Before that point, a change written between the build reading a file and the watcher's baseline would be missed for good. It runs concurrently with the initial generate and the merger validation. Once validation is out of it, arming is the target walk, fsnotify adds and source hashing (~0.3s on eos). (My call.)

- When the initial generate finishes with **no writes and no removals** in any dir, the speculative build's result is used:
  - on success, and once merger validation has passed (section 2), `run` starts (`restartNoBuild`) and startup continues as today: the phase becomes `starting`, then health is checked;
  - on failure, the build error is reported exactly as today's initial build failure.
- When the initial generate **writes or removes any file**, the speculative build is cancelled (context cancel, and its output discarded), and a normal `rebuild` runs after the writes, as today.
- When the initial generate **fails** (today's `startOK == false`), the speculative build is cancelled and no initial build runs, as today.

Split `devServer.rebuild` into its build step and `restartNoBuild` so the speculative path can use them separately. The build command, directory, environment and output wiring are identical in both paths.

### 4. Background warm-up

Once startup has finished (the server is healthy, or startup is done if the build failed), one warm-up job starts. It runs `regenDirs` over the dirs that were cache hits, through the session Module. That completes the world load, the analysis, the import graph and the per-dir source publication that today's initial generate did up front.

- **It runs off the event-loop goroutine.** Ctrl-C, `ctx` cancellation, `.env` restarts and panel commands that don't generate (`restart-server`) stay responsive. (My call.)
- **Every edit cycle (and the panel `rebuild` command) waits for the warm-up to finish before it runs.** Before warm-up, the Module's import graph covers only the misses' closures, so `Dependents` would miss dependents of a shared component or helper, and the loop would serve stale `.x.go`. Waiting is the accepted tradeoff. (My call.)
- **It posts nothing** to the overlay or panel when it writes nothing, so a startup build-error or codegen-error overlay is not cleared. (My call.)
- **If it writes anything** (cache hit output ≠ Module output), it is handled exactly like an edit cycle: written, reported and rebuilt. This should never happen; if it does, it reveals a cache defect.

## Verification

- **Existing tests stay green.** `gsx dev`/watch tests (`gen` `TestDev*`, `TestWatch*`) and the corpus.
- **Equivalence test.** For one fixture module with several dirs (with and without warnings), an orphan and a miss, today's initial generate and the new cached startup produce identical `cycleResult`s, apart from `DurMs`, and identical files on disk.
- **Speculative build tests.**
  - With no writes, the build runs once and the server starts from it.
  - If the generate writes, the speculative build is cancelled and exactly one rebuild follows. Test this with a build command that records its invocations.
  - If the generate fails, there is no build.
  - If the build fails with no writes, the build error is reported once.
- **Warm-up tests.**
  - An edit arriving during warm-up waits for it, then regenerates every dependent dir (a shared-component edit regenerates its importers).
  - Ctrl-C during warm-up exits promptly.
  - Warm-up writes and posts nothing on an up-to-date tree, and a startup error overlay survives it.
- **Merger validation.** A bad merger still exits 1 with the same text, and `run` is never started.
- **Speculative build ordering.** A `.go` edit landing between arming and build completion is caught: the build's result is discarded, or the edit triggers the next cycle.
- **eos.** `task dev` in a fresh linked worktree reaches a healthy server with gsx no longer on the critical path. Measure startup on an idle machine against v0.4.4. The `.x.go` files are byte-identical.
